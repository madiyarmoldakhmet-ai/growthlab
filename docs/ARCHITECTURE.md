# Growth Lab Architecture

## 1. Назначение проекта

Growth Lab - платформа для управления ростом через исходящие коммуникации: контакты, кампании, сообщения, ответы лидов, WhatsApp-подключение и AI-помощь для генерации текстов и оценки реакции.

Система должна помогать команде:

- импортировать и очищать базу контактов;
- создавать кампании;
- генерировать персонализированные сообщения;
- отправлять сообщения по доступным каналам;
- получать и анализировать ответы;
- классифицировать лидов по интересу;
- видеть состояние кампаний и коммуникаций.

## 2. Текущий контекст репозитория

В проекте уже присутствуют backend и frontend-файлы. Эта документация не изменяет код и описывает целевую архитектуру вокруг уже видимых доменов:

- `auth` - вход, выход, JWT, роли `admin` и `member`;
- `contacts` - CRUD, импорт CSV/Excel, дедупликация;
- `campaigns` - CRUD и статусы кампаний;
- `whatsapp` - подключение, QR, отправка, входящие сообщения, статусы;
- `ai` - генерация сообщений, улучшение текста, классификация лидов, оценка ответов;
- `prisma` - PostgreSQL-модель пользователей, контактов, кампаний, сообщений, ответов и настроек.

## 3. Границы продукта

### Входит в продукт

- Авторизация пользователей.
- Управление контактами.
- Импорт контактов из CSV и Excel.
- Дедупликация контактов.
- Управление кампаниями.
- Создание и хранение сообщений.
- Отправка WhatsApp-сообщений.
- Получение входящих ответов.
- AI-генерация сообщений.
- AI-классификация лидов.
- Настройки пользователя и интеграций.
- Базовая аналитика кампаний.

### Не входит в ближайший объем

- Полноценная CRM с воронками сделок.
- Встроенная телефония.
- Сложная маркетинговая автоматизация.
- Собственный email-сервер.
- Сквозная финансовая аналитика.
- Мультиаккаунтная enterprise-иерархия.

## 4. Пользовательские роли

### Admin

Управляет пользователями, системными настройками, интеграциями, доступами и может видеть административные проверки.

### Member

Работает с контактами, кампаниями, сообщениями, ответами и AI-инструментами в рамках своего аккаунта.

В будущем роли можно расширить до:

- owner;
- manager;
- sales;
- marketer;
- viewer.

## 5. Основные домены

### Identity

Пользователи, роли, JWT-сессии, logout, защита эндпоинтов.

### Contacts

Единая база лидов и клиентов. Контакт может иметь email, телефон, имя, фамилию, компанию и дополнительные metadata.

### Campaigns

Группировка коммуникаций вокруг одной цели: запуск, прогрев, реактивация, приглашение, исследование спроса.

### Messages

Исходящие сообщения по каналам. Минимальные каналы: WhatsApp и email как логический канал для генерации. Фактическая отправка на текущем этапе сфокусирована на WhatsApp.

### Responses

Входящие ответы лидов, связанные с сообщением, контактом и кампанией.

### AI Assistance

AI-слой помогает:

- генерировать сообщение под продукт, аудиторию, цель и тон;
- улучшать текст;
- классифицировать ответ лида;
- оценивать ответ и предлагать следующее действие.

### Settings

Пользовательские и системные настройки: ключи интеграций, предпочтения каналов, параметры AI, лимиты, шаблоны.

## 6. Архитектурный стиль

Рекомендуемый стиль - модульный монолит.

Причины:

- домен еще развивается;
- модули уже разделены по бизнес-областям;
- проще поддерживать транзакционную целостность;
- быстрее развивать продукт без сетевой сложности микросервисов;
- границы модулей можно сохранить для будущего выделения сервисов.

Рекомендуемые модули:

- AuthModule;
- UsersModule;
- ContactsModule;
- CampaignsModule;
- MessagesModule;
- ResponsesModule;
- WhatsappModule;
- AiModule;
- SettingsModule;
- AnalyticsModule;
- ImportsModule.

## 7. Слои системы

### Presentation Layer

Web-интерфейс для пользователя. Документация не требует создания frontend, но будущий интерфейс должен опираться на API из `API.md`.

### API Layer

HTTP JSON API. Отвечает за маршруты, DTO, валидацию, авторизацию, коды ошибок и единый формат ответов.

### Domain Layer

Бизнес-логика:

- нормализация контактов;
- поиск дублей;
- переходы статусов кампаний;
- создание сообщений;
- обработка статусов доставки;
- классификация ответов;
- расчет показателей кампаний.

### Persistence Layer

PostgreSQL через Prisma. База является источником истины для пользователей, контактов, кампаний, сообщений, ответов и настроек.

### Integration Layer

Адаптеры внешних сервисов:

- WhatsApp provider;
- OpenAI-compatible AI provider;
- будущие email/SMS/CRM/analytics providers.

### Background Jobs

Нужны для:

- массовой отправки сообщений;
- ретраев доставки;
- обработки входящих событий;
- импорта файлов;
- AI-обработки пачек ответов;
- пересчета аналитики.

## 8. Ключевые сценарии

### Импорт и очистка контактов

1. Пользователь загружает CSV или Excel.
2. Система читает строки и сопоставляет известные поля.
3. Контакты нормализуются.
4. Дубли ищутся по email или телефону.
5. Пользователь получает результат: импортировано, пропущено дублей, список контактов.

### Создание кампании

1. Пользователь создает кампанию.
2. Кампания стартует в статусе `draft`.
3. Пользователь добавляет описание, даты и целевые контакты.
4. Кампания переводится в `active`.
5. Система разрешает отправку сообщений.

### AI-подготовка сообщения

1. Пользователь указывает продукт, аудиторию, цель, канал и тон.
2. AI генерирует subject и body.
3. Пользователь редактирует текст.
4. Сообщение сохраняется или отправляется.

### WhatsApp-отправка

1. Пользователь подключает WhatsApp.
2. Система возвращает QR или статус подключения.
3. Пользователь отправляет сообщение контакту.
4. Сообщение получает статус `queued`, `sent`, `delivered` или `failed`.
5. Входящие ответы сохраняются как responses.

### AI-оценка ответа

1. Система получает ответ лида.
2. AI классифицирует категорию: интерес, цена, созвон, не интересно, перезвонить позже.
3. AI возвращает score, summary и nextAction.
4. Пользователь видит рекомендуемый следующий шаг.

## 9. Статусы

### CampaignStatus

- `draft` - кампания готовится;
- `active` - кампания запущена;
- `paused` - временно остановлена;
- `completed` - завершена;
- `archived` - скрыта из активной работы.

### MessageStatus

- `queued` - ожидает отправки;
- `sent` - отправлено провайдеру;
- `delivered` - доставлено получателю;
- `failed` - отправка не удалась.

### LeadCategory

Рекомендуемые категории:

- `interest`;
- `not_interested`;
- `price`;
- `call`;
- `follow_up_later`.

Текущий код содержит русские категории; целевая архитектура должна нормализовать их до стабильных enum-значений и отображать локализованные подписи на уровне интерфейса.

## 10. Безопасность

Требования:

- хранить пароли только как password hash;
- защищать приватные endpoint'ы JWT guard'ом;
- проверять роль admin на административных endpoint'ах;
- изолировать данные по `user_id`, пока нет workspaces;
- не хранить plaintext-токены интеграций;
- шифровать credentials для WhatsApp, AI и будущих провайдеров;
- логировать критические действия без записи секретов.

## 11. Данные и владение

Текущая модель построена вокруг пользователя как владельца данных. Все ключевые сущности должны быть связаны с `user_id`.

В будущем можно перейти к workspace-модели:

- workspace;
- membership;
- role;
- shared contacts;
- shared campaigns.

Но для текущего проекта корректная ближайшая цель - стабилизировать user-scoped модель.

## 12. Наблюдаемость

Нужно фиксировать:

- ошибки авторизации;
- ошибки импорта;
- ошибки WhatsApp-подключения;
- ошибки отправки сообщений;
- ошибки AI-запросов;
- длительность массовых операций;
- количество отправленных, доставленных и failed сообщений.

Рекомендуемые компоненты:

- structured logs;
- request id;
- error tracking;
- job monitoring;
- integration event logs.

## 13. Аналитика

Первичные показатели:

- количество контактов;
- количество кампаний по статусам;
- количество сообщений по статусам;
- delivery rate;
- response rate;
- positive response rate;
- количество лидов по AI-категориям;
- средний lead score;
- конверсия кампании в созвон.

## 14. Целевые архитектурные решения

- PostgreSQL остается основным хранилищем.
- Prisma используется как слой доступа к данным.
- WhatsApp изолируется за сервисным адаптером.
- AI изолируется за провайдером с fallback-логикой.
- Массовые операции выносятся в background jobs.
- API должен перейти к единому response envelope.
- Данные должны быть persistable, без in-memory Map для production-потоков.

## 15. Принципы развития

- Сначала надежность контактов и сообщений, потом сложная автоматизация.
- Пользователь всегда подтверждает AI-текст перед массовой отправкой.
- Интеграции не должны ломать core-domain при отказе внешнего сервиса.
- Все коммуникации должны быть трассируемыми до кампании, контакта и пользователя.
- Статусы должны быть enum, а не произвольные строки.
